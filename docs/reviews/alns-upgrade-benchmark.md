# Воспроизводимое сравнение версий ALNS

Стенд `scripts/benchmark_alns_upgrade.py` сравнивает версии приложения на одинаковых сохранённых данных. Он не переносит результаты из `core_results.html`: там 35 модельных инженеров, длительности 30–45 минут, локальные стартовые базы и сравнение лучшего из трёх запусков ядра около 30 секунд с OR-Tools за 120 секунд. В `alns-comparison.md` используются сценарии приложения, по 15 инженеров на участок, нормативы приложения, дорожные/комбинированные матрицы, приоритеты аварий и подключений и бюджеты 3/10 секунд. Числа из этих двух опытов напрямую несопоставимы.

## Запуск

Сначала сохранить старую версию в отдельный каталог, например через `git archive`. Этот каталог должен содержать `src/field_router`. Зависимости берутся из интерпретатора запуска: обе версии используют одно окружение. Пример полного сравнения исходных бригад:

```sh
.venv/bin/python scripts/benchmark_alns_upgrade.py \
  --code-root before=/private/tmp/field-router-alns-before \
  --revision before=aac4375 \
  --code-root after="$PWD" \
  --seconds 3 10 --seeds 0 1 2 \
  --solvers ortools alns hybrid --stock morning issued \
  --output docs/reviews/alns-upgrade-stock.json
```

Это 168 последовательных запусков для трёх регионов и двух версий, суммарно 1092 секунды заданного поискового времени плюс подготовка и проверка. OR-Tools запускается один раз на регион, запас, бюджет и профиль, поскольку интерфейс не принимает seed. По умолчанию стенд использует один кодовый каталог, 3 секунды, seed 0 и утренний запас: девять запусков, 27 секунд поискового времени.

Сокращённый опыт на одном регионе:

```sh
.venv/bin/python scripts/benchmark_alns_upgrade.py \
  --code-root before=/private/tmp/field-router-alns-before --code-root after="$PWD" \
  --regions Восток --seconds 3 --seeds 0 --solvers alns hybrid \
  --output /private/tmp/alns-upgrade-smoke.json
```

`--dry-run` сохраняет сценарии и перечень запусков без расчёта. Для продолжения нужен тот же вызов с `--resume` вместо `--dry-run`. `--resume` пропускает уже записанные строки, включая ошибки, и отказывается продолжать при изменении кода, сценариев, параметров или самого стенда. Для повторения ошибочных строк используйте новый файл результата и соответствующий сокращённый набор параметров.

## Варианты бригад и сохранённый план

`--fleet-seeds` без значений добавляет пять вариантов с seed 0–4 к исходному составу. `--fleet-seeds 1 4` добавляет только два указанных варианта. Меняются независимыми перестановками только навыки, транспорт и связка «стартовая точка + адрес старта + смена». Их исходные распределения и число инженеров сохраняются в точности. Новые координаты, смены, нормативы работ и оборудование не генерируются. Варианты разрешены только для бригад, явно помеченных `engineers_source=synthetic`.

В режиме `issued` оборудование сначала фиксируется по исходному сохранённому плану OR-Tools и остаётся у соответствующего ID инженера при перестановке его остальных свойств. Поэтому варианты с выданным запасом — стресс поиска при изменившемся составе; это не воспроизведение исполненного рабочего дня. Исходный сохранённый план может оказаться недопустимым для такого варианта; стенд записывает нарушения исходного плана отдельно, а каждый новый результат проверяет полностью.

Пример ограниченной проверки пяти вариантов:

```sh
.venv/bin/python scripts/benchmark_alns_upgrade.py \
  --code-root before=/private/tmp/field-router-alns-before --code-root after="$PWD" \
  --seconds 3 --seeds 0 --solvers alns hybrid --stock morning \
  --fleet-seeds --output docs/reviews/alns-upgrade-fleets.json
```

`--reference saved` передаёт всем методам один и тот же сохранённый план OR-Tools. `--profiles cost sla stable` выбирает профили; по умолчанию используется `cost`. Для `stable` требуется `--reference saved`. Такой опыт проверяет сохранение/перестройку расписания без событий дня; отмены, факты выполнения, аварии и недоступность инженеров отдельно проверяет `scripts/check_resilience.py`.

```sh
.venv/bin/python scripts/benchmark_alns_upgrade.py \
  --code-root before=/private/tmp/field-router-alns-before --code-root after="$PWD" \
  --seconds 3 --seeds 0 1 2 --stock issued --reference saved \
  --profiles stable --output docs/reviews/alns-upgrade-stable.json
```

## Что сохраняется

Подготовка выполняется кодом первого каталога один раз. Эффективный сценарий и reference сохраняются рядом с JSON результата в каталоге `<имя-результата>-cases`. Каждый измеряемый запуск загружает одни и те же файлы сценария и исходной географии. Исходные файлы не изменяются. Проверяются SHA-256 исходного файла, эффективного сценария, reference и исходников версии; изменение кода во время запуска делает строку ошибочной.

Для каждого результата записываются:

- назначенные и общее число заявок по каждому приоритету; лексикографическая цель;
- бригады, метры/километры, время поездок и работы, неназначенные ID;
- стеночное время и процессорное время вызова `solve`, отдельно полное время дочернего процесса; импорты, подготовка и независимая проверка исключены из времени `solve`;
- полный план, ошибки независимого `validate_plan`, статус, исходная диагностика и счётчики итераций по стадиям;
- путь к версии, Git revision, при необходимости явно указанная ревизия архива, хеш исходников и версии Python/зависимостей.

Одновременно работает только один дочерний процесс; порядок версий внутри пар чередуется. Строка записывается атомарно после каждого запуска, включая ошибки и таймауты. Для измерений следует остановить другие тесты и CPU-задачи. Wall-clock ограничение и потоки численных библиотек не дают побитной воспроизводимости; seed фиксирует случайный выбор, а не точное число итераций. Процессорное время учитывает потоки внутри процесса. Ограничения BLAS/OpenMP в окружении не заменяют внутренние параметры CP-SAT.

Сравнивать следует все строки с одинаковыми хешами эффективного сценария/reference, бюджетом и профилем. Сначала сравнивается охват по приоритетам, затем профиль, бригады и метры; выбор только лучшего seed скрывает нестабильность. Стенд сохраняет исходные результаты и сам не делает вывод о превосходстве ALNS или необходимости гибрида.
