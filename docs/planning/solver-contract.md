# Контракт первого расчета дня

Доступны `OrToolsSolver`, `AlnsSolver` и `HybridSolver`; `BaselineSolver` служит эталоном из ТЗ. Они используют общий контракт `Scenario / TravelProvider / Plan`:

```python
solve(scenario: Scenario, travel: TravelProvider, *, time_limit_seconds: float = 5) -> Plan
```

`Scenario` содержит неизменяемые по атрибутам Pydantic-модели заявок и инженеров, офис, одну зону/дату, происхождение и параметры. Списки/словари внутри моделей следует считать входными только для чтения. Пример полного входа после демо: `output/demo/Восток/scenario.json`. JSON-схемы находятся в `docs/contracts/`.

`TravelProvider.minutes(origin, destination, mode)` и `.metres(...)` возвращают целые неотрицательные значения. Идентификаторы: `request.id` и `engineer.start_location`; транспорта четыре. `MatrixTravel` позволяет подать разные готовые матрицы по типам транспорта, включая асимметричные. CLI использует синтетический провайдер либо явно переданный полный набор географии и матриц.

Время — минуты от начала московского дня. Окна ограничивают начало включительно. Время обслуживания входит в смену отдельно от дороги. Раннее прибытие допускает ожидание; возврат не требуется. Навык, участок, требуемый транспорт и заданные остатки устройств — жесткие ограничения.

Выход `Plan`: последовательности посещений с прибытием/началом/концом, дорога и работа отдельно, выдача устройств, метрики, неназначенные с причинами, время и статус поиска. Каждая исходная заявка встречается ровно один раз: назначенная или неназначенная. Неизвестные ID запрещены.

После расчета обязательно `require_valid(scenario, travel, plan)`; HTML/JSON публикуются только при отсутствии нарушений. Валидатор независимо пересчитывает ограничения и агрегаты. `SEARCH_UNASSIGNED` означает отсутствие назначения в найденном плане, а не доказанную невозможность обслуживания.

В OR-Tools порядок целей: минимум неназначенных аварий → минимум неназначенных подключений → минимум всех неназначенных → профильные показатели. Значения `urgent > high > normal`. Сначала строится решение по авариям, затем найденный охват защищается нижней границей во втором поиске. Остальные цели разделены доминирующими целочисленными штрафами. Проверка кандидата использует тот же лексикографический порядок. Лимит времени не гарантирует максимальный охват; диагностика явно указывает отсутствие доказанного оптимума.

Приоритеты — согласованная пересматриваемая политика обогащения, а не новое поле исходного CSV. Правило `config/demo.json → work_rules → priority` задает `Подключение=high`, `Глобальная проблема=urgent`, `Дозаказ=normal`, `Локальная заявка=normal`. Отсутствие поля означает `normal`. Окна начала/окончания и порядок строк CSV сохраняются без изменений. Baseline по-прежнему обрабатывает исходный порядок, выбирает первого подходящего инженера и добавляет работу только в конец маршрута; приоритет не меняет этот эталонный алгоритм.

Временной лимит не доказывает оптимум; неудача поиска или ухудшение целевого кортежа приводит к явно обозначенному baseline.

Документация OR-Tools: [временные окна](https://developers.google.com/optimization/routing/vrptw), [необязательные посещения и штрафы](https://developers.google.com/optimization/routing/penalties).

События, остатки на момент события и закреплённые действия обрабатывает `ScenarioSession`: оптимизатор получает остаточную задачу и reference. PlanDiff вычисляется снаружи оптимизатора.

### Обновление 20.09.2026

Предыдущая политика равенства urgent/high заменена: urgent > high > normal. objective_key сравнивает число неназначенных аварий, затем подключений (через совокупный охват urgent/high при равном urgent), затем всех заявок, затем профильные показатели. OR-Tools получает стартовое решение по авариям и нижнюю границу их охвата перед вторым поиском. Диагностика отражает emergency_coverage_floor. С 22.09 веса кодируют безопасный точный префикс: search_omitted_tiers перечисляет вторичные цели, не поместившиеся в поисковые веса. Финальное сравнение использует все цели и точные метры; search_distance_unit_metres=1. Статический baseline сохраняет порядок из ТЗ.


### ALNS и совместный backend (21.09.2026)

`AlnsSolver.solve` поддерживает тот же Scenario/TravelProvider/Plan, profile и reference; дополнительно seed и initial_plan. Все четыре режима передаются матрицами без fallback. `HybridSolver` сохраняет лучший результат OR-Tools, ALNS и допустимого reference по общей objective_key. Операционную задачу формирует ScenarioSession, не standalone replan сокомандника. Приоритеты, оборудование, несколько окон и последний сервис перед концом смены проверяются внутри ядра и независимым require_valid. Глобальные сертификаты отключены.

CLI и сервер принимают --solver ortools|alns|hybrid. По умолчанию сервер и утренняя настройка бригад используют hybrid. Бюджет сервера относится к одному из трёх профилей; общий отклик примерно в три раза больше плюс подготовка/проверки.

### Усиленный ALNS (21.09.2026)

Промежуточный поиск допускает ограниченное ухудшение и перезапуски для выхода из локального решения. Публикуемый лучший план сравнивается строго, без размена приоритетов. Все найденные допустимые маршруты могут пополнять ограниченный пул, даже если полный промежуточный план хуже. CP-SAT объединяет цели безопасными весами, рассчитанными из верхних границ; при больших коэффициентах разделяет их на этапы. Это точная иерархия внутри ограниченного пула, не сертификат глобального оптимума.

Профиль stable оптимизирует ожидание в фиксированном порядке: сумма модулей отклонений от reference минимальна по целочисленным минутам, при сохранении всех окон и ограничений. Результат экспортируется с этими же временами и проходит независимую проверку. Оптимальность порядка/назначений не заявляется. При шести секундах и более непосредственно в ядре выполняются два раунда поиска с промежуточной сборкой маршрутов; короткий бюджет использует одну сборку. Параллельные процессы не запускаются.

### Дневные стратегии (22.09.2026)

Единый компаратор находится в `objectives.py`. После общего охвата:

| profile | Минимизируется последовательно |
|---|---|
| None, утро | занятые бригады → метры |
| stable | предотвратимые смены исполнителя → абсолютные сдвиги начал → минуты дороги → метры → бригады |
| cost | минуты дороги → метры → смены исполнителя → сдвиги → бригады |
| sla | оценка реакции → смены исполнителя → сдвиги → минуты дороги → метры → бригады |

`focus_request_id` — явно переданный ID новой аварии; допустим только urgent. Без него SLA ускоряет все оставшиеся urgent, без urgent совпадает со Stable. Оценка реакции — сумма начал назначенных целей плюс 1441 за каждую неназначенную. Время старого клиента учитывается и после выбытия исполнителя; неизбежное переназначение с выбывшего исполнителя не входит в штраф. Ожидание теперь оптимизируется для всех дневных профилей; SLA сначала защищает реакцию.

`ScenarioSession.preview` сравнивает общий пул по каждой цели. Возвращает три ID для совместимости API, `duplicate_of` и `strategy_ids` группируют совпадающие маршруты/времена, `recommended_candidate_id` — рекомендацию по серверному правилу. ИИ объясняет эту рекомендацию и не меняет её. Утверждение проверяет версию, пакет и допустимость и остаётся отдельным действием диспетчера.

### Сохранение короткого результата (22.09.2026)

Hybrid делит общий бюджет T на короткий этап `min(T, 3)` и продолжение. В коротком этапе OR-Tools получает 40%, ALNS — оставшееся время этапа. Лучший проверенный результат OR-Tools, ALNS и допустимого reference сохраняется. Если T больше 3, следующий поиск ALNS получает этот план и остаток **общего** бюджета; seed увеличивается на 1. Каждое улучшение проверяется `require_valid` и полным `objective_key` текущего профиля. При ухудшении, недопустимом ответе или исключении ALNS сохранённый план остаётся доступен. Подготовка/остановка и финальная валидация могут слегка превысить бюджет.

`HybridSolver.solve(..., initial_plan=previous_plan)` позволяет передать фактический результат отдельного расчёта. План обязан быть допустим для текущего сценария и матриц; неверный вход отклоняется до поиска. `initial_plan` не заменяет `reference`, который по-прежнему задаёт обещания клиентам и стабильность. Состояние поиска и пул маршрутов между этапами не переносятся, переносится лучший план. Независимые вызовы без общего исходного плана могут отличаться из-за ограничения по реальному времени; глобальная монотонность результатов таких вызовов не заявляется.

Диагностика содержит `checkpoint` (бюджет, фактическое время, полный ключ и метрики короткого этапа), `continuation` (остаток бюджета, seed, улучшение, диагностика или ошибка ALNS), итоговый `objective_key`. Повторяемый эксперимент: `python scripts/check_hybrid_continuation.py --output output/hybrid-continuation.json`; он выполняет отдельные 3 и 10 секунд на регион, передавая первый план во второй вызов.
