## Подтверждённые ограничения и дефекты

1. **Динамика: выезд до события.** replan.py:58 меняет нижнюю границу окна, но не актуализирует позицию и доступность инженера. Контрпример: инженер свободен, новая авария поступила в 12:00, дорога 60 минут. Результат replan: выезд 11:00, начало работ 12:00. Собственный валидатор принимает план. Нельзя использовать этот replan вместо нашего ScenarioSession.
2. **Приоритеты.** io.py:85 допускает только два уровня; solution.py:11 и solver.weighted_unassigned задают отношение 10:1. На одном инженере со сменой 11 минут план с 11 обычными работами по минуте считается лучше одной аварии на 11 минут. Оба плана допустимы. Отдельного приоритета подключения нет. Нужен строгий порядок авария → подключение → ремонт/дозаказ во всех этапах оптимизации.
3. **Оборудование отсутствует в модели и проверке.** Дополнительные поля equipment молча игнорируются парсером. В проверке заявка с routers=1 назначена инженеру с routers=0. Требуется полноценное ограничение суммарного расхода по маршруту, включая остатки при перепланировании; одной проверки совместимости заявки недостаточно.
4. **Нижние границы требуют исправления для неметрических матриц.** cg.py:34 исключает из pricing заявку, недостижимую прямым стартовым плечом. Контрпример: старт→A=10 мин, работа A=10, A→B=10, старт→B=120; B доступна до 10:00, смена начинается в 09:00. Маршрут A→B допустим, но ColumnGeneration без исходного пула возвращает solve_phase('U')=(1.0, True): якобы минимум одна неназначенная вместо достижимого нуля. Это проверка отдельного компонента CG, не утверждение, что каждый запуск полного solve выдаст неверный сертификат. Начальный пул ALNS может скрывать дефект. Для наших матриц такой фильтр небезопасен. Полного математического аудита остальных отсечений не проводилось.
5. **Данные примеров устарели относительно уточнений организаторов.** prepare_beeline.py использует собственные длительности по HD (например авария 60), свою модель обязательного автомобиля и бригад. Нужны наши нормализованные длительности, фактическая дорога вместо 20 минут и одинаковый состав ресурсов.
6. **Упрощённая география по умолчанию.** instance.py рассчитывает расстояние по прямой с коэффициентами; transit — средняя скорость плюс ожидание. Использовать только наши полные внешние матрицы, без неявного fallback отсутствующего режима.
7. **Контракт приложения шире.** Ядро хранит одно окно на заявку и один требуемый навык; нет наших остатков, фактических статусов, версий, диспетчерских разрешений и трёх сценарных целей. plan_from_dict восстанавливает последовательность, игнорируя переданное фактическое расписание.
8. **Нет общего жёсткого лимита времени.** Параметр API time_limit относится только к OR-Tools. fleet_time расходуется на каждую попытку сокращения парка; CP-SAT выделяет минимум секунду каждому этапу, даже после дедлайна. Для UI нужен общий бюджет и безопасный возврат лучшего плана.

## Предлагаемая интеграция

1. Сохранить наше приложение, географию, ScenarioSession и независимый валидатор. ALNS подключать как дополнительный backend через адаптер нормализованной задачи; каждый регион отдельно.
2. Сначала добавить оборудование, строгие три приоритета и необходимые оконные ограничения. Исправить CG либо отключить сертификаты до доказательства корректности на наших матрицах.
3. Динамический остаток дня формировать нашим слоем: текущая позиция/время, зафиксированная работа, исключение закрытых заявок, остатки оборудования.
4. Сравнить OR-Tools и ALNS на одинаковых входах, целях и бюджетах, с несколькими seed, включая сценарии рабочего дня. Любой результат проверять нашим валидатором; при ошибке/таймауте сохранять прежний допустимый план.
5. Только после этих проверок выбирать основной backend или портфель двух алгоритмов. Улучшение числа назначений не обещать до сопоставимого эксперимента.
