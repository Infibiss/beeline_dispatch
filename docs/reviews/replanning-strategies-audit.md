# Аудит стратегий пересчёта

**Исторический аудит до изменений.** Предложенная дневная политика принята пользователем и реализована 22.09; действующий контракт — [план реализации](../planning/operational-strategies-plan.md), результаты — [проверка новых стратегий](operational-strategies.md). Ниже сохранено исходное состояние для объяснения причин изменения.

Дата: 22 сентября 2026. Проверены действующие цели, общий пул предложений, интерфейс, рекомендации LLM, адаптер ALNS и сохранённые результаты предыдущего эксперимента. Код приложения не менялся. Это разбор текущей реализации и предложение следующей политики, а не новый сравнительный бенчмарк.

## Почему Stable часто выглядит лучшим

Все три варианта сначала максимизируют один и тот же охват. Затем `preview` выбирает каждый вариант **из общего пула** трёх найденных планов. Поэтому найденное одним поиском улучшение охвата доступно всем стратегиям. Если только один план имеет лучший охват, все три карточки обязаны выбрать его независимо от вторичных целей. Совпадение не означает, что три цели одинаковы или алгоритм обязательно сломан.

При неизменном допустимом расписании Stable естественно сохраняет назначения и время; срочного выигрыша может не быть, а переупорядочение только создаст лишние изменения. Есть и проблема сравнения: основной показатель SLA — сумма времени начала всех приоритетных работ — в таблице не показан. Вместо него показано начало **новой** аварии. Cost минимизирует сначала число используемых инженеров, затем метры, хотя в объяснениях LLM сравниваются минуты дороги. Это разные задачи.

Источник: [общий пул и выбор](../../src/field_router/replanning.py#L379), [точные цели](../../src/field_router/solvers/ortools_solver.py#L28), [таблица интерфейса](../../src/field_router/static/scenarios.js#L307).

## Точный порядок действующих приоритетов

Сравнение лексикографическое: следующий показатель имеет значение только при равенстве всех предыдущих. Это не сумма условных денежных штрафов.

Общий префикс всех целей: `(неназначенные urgent, неназначенные urgent+high, все неназначенные)`. При равенстве urgent второй компонент эквивалентен сравнению только подключений (`high`). Иными словами: аварии → подключения → остальные заявки. Это жёсткий приоритет сравнения найденных допустимых планов; утверждения, что все заявки обязательно назначены или глобальный максимум доказан, нет.

| Профиль | Затем минимизирует | Чего цель не обещает |
|---|---|---|
| SLA-first / «Раньше приоритетные» | Сумму минут начала **всех** urgent и high → инженеров → метры | Самую быструю реакцию именно на новую аварию; выполнение отдельного нормативного SLA; минимум изменений |
| Stable / «Меньше изменений» | Число смен исполнителя → сумму абсолютных сдвигов начала → инженеров → метры | Минимум количества сдвинутых заявок; сохранение каждого прежнего назначения; самый короткий путь |
| Cost-first / «Меньше ресурсов» | Число инженеров с непустым маршрутом → метры | Минимум минут дороги, рублей, топлива либо числа изменений |

В Stable сравниваются только назначенные в обоих планах заявки, чей прежний инженер присутствует в оставшемся сценарии. Переназначение с выбывшего инженера не штрафуется: оно неизбежно. Но вместе с ним исключается и старое время этой заявки, даже если клиентское обещание времени всё ещё актуально. В `facts` UI считает все смены и сдвиги, включая этот случай. Потому отображаемый счётчик может не совпасть с частью целевой функции. Потери прежних назначений (`lost_assignments`) показываются, но не являются самостоятельным компонентом ни одной цели: при равном охвате одну старую заявку можно заменить другой.

Источники: [фильтр reference и цели](../../src/field_router/solvers/ortools_solver.py#L18), [отображаемые факты](../../src/field_router/replanning.py#L48), [регрессия выбывшего инженера](../../tests/test_scenario_objectives.py#L42).

OR-Tools задаёт масштабированные целочисленные стоимости и защищённый нижний предел охвата аварий из предварительного поиска; затем сравнивает результат с допустимым резервным планом по `objective_key`. ALNS переносит те же приоритеты в ядро, оптимизирует ожидание Stable и проверяет экспортированный план тем же компаратором. Hybrid отдаёт примерно 40% бюджета OR-Tools, остаток ALNS и сохраняет лучший найденный вариант. Ограниченное время поиска не доказывает оптимальность. Источники: [OR-Tools](../../src/field_router/solvers/ortools_solver.py), [адаптер ALNS](../../src/field_router/solvers/alns_solver.py#L81), [цели ядра](../../src/field_router/_alns/solution.py#L90), [Hybrid](../../src/field_router/solvers/selection.py#L10).

## Общий пул и совпадения

`preview` последовательно выполняет `solve(sla)`, `solve(stable)`, `solve(cost)`, после чего трижды выбирает `min(pool, objective_key(profile))`. Следствия:

- У всех трёх показанных вариантов одинаковый лучший в пуле вектор охвата, включая общее число назначений. Причина — общий приоритетный префикс.
- SLA не может проиграть Stable по своей полной цели, а Cost — по своей, **внутри этого пула**. Отдельные показатели могут быть хуже: например, меньше инженеров ценой большего пути.
- При полном равенстве ключей `min` берёт первый план из пула; порядок — SLA, Stable, Cost. Это не скрытое преимущество Stable.
- `duplicate_of` сравнивает отображение `request_id → (engineer_id, start)`. Три карточки показываются даже при одном уникальном расписании. Корректнее показывать одну карточку с перечислением совпавших целей, а не создавать искусственно худшие альтернативы.

Если Stable лучше по всем **показанным** строкам, это ещё не доказывает доминирование по SLA: скрытая сумма начал может быть больше. Для строгого вывода следует сравнивать и охват, и профильные показатели, и сохранение назначений, и эксплуатационные ресурсы. Равенство всех этих показателей следует отдельно отличать от строгого доминирования хотя бы по одному.

## Ограниченные проверенные примеры

Текущие `tests/test_scenario_objectives.py`: **13 passed** за 1.98 с (три прежних предупреждения SWIG). В частности, уже есть тест: SLA начинает high и urgent в минуту 600 двумя инженерами, а Cost использует одного. Это контрпример утверждению, что цели никогда не различаются.

Дополнительно выполнен маленький расчёт текущим OR-Tools, по 0.1 с на профиль, с общей повторной выборкой как в `preview`. Две работы по 30 мин, окна 600–720, два одинаковых инженера со сменой 540–1080; между разными точками 10 мин / 1 км. В исходном допустимом плане каждый инженер получает одну работу с началом в 680. Одна работа high, одна urgent. Все полученные планы прошли `require_valid`.

| Показатель | SLA | Stable | Cost |
|---|---:|---:|---:|
| Назначено | 2/2 | 2/2 | 2/2 |
| Начала работ | 600 и 600 | 680 и 680 | 600 и 640 |
| Сумма начал приоритетных | 1200 | 1360 | 1240 |
| Инженеров | 2 | 2 | 1 |
| Смен исполнителя в этом запуске | 2 | 0 | 1 |
| Абсолютные сдвиги, мин | 160 | 0 | 120 |
| Дорога, мин / км | 20 / 2 | 20 / 2 | 20 / 2 |

Здесь все три выбранных расписания различаются: SLA раньше, Stable сохраняет обещания, Cost освобождает одного инженера. Это учебный свидетель различия целей, **не** замер частоты выигрышей на дорожных данных. Конкретная идентичность исполнителей при симметричных инженерах может меняться; для бизнес-смысла достаточно показанных времён и числа инженеров.

Сохранённые [156 строк ALNS-эксперимента](alns-upgrade-results.json) имеют только профиль `cost` и не подходят для сравнения трёх стратегий. Дневные [ALNS](alns-upgrade-day-alns/day-resilience.json) и [hybrid](alns-upgrade-day-hybrid/day-resilience.json) отчёты содержат 48 этапов в сумме и проверку всех 144 предложений, однако сохраняют показатели **утверждённого Stable**, без двух альтернатив и сигнатур. [Скрипт](../../scripts/check_resilience.py#L103) явно выбирает Stable. По этим файлам нельзя посчитать ни долю дубликатов, ни частоту доминирования Stable. Предыдущий [обзор обновления](alns-upgrade.md) корректно предупреждает об ограничениях времени и не доказывает превосходство стратегии Stable.

## Несогласованность рекомендации

Резервное правило LLM: аварии → подключения → реакция на новую аварию → общий охват → смены исполнителя → минуты сдвигов → **минуты дороги** → при равенстве Stable. Порядок реакции и общего охвата отличается от solver; в текущем общем пуле расхождение не меняет охват, поскольку он уже одинаков. Но это разные контракты и риск при расширении пула.

LLM разрешён выбор среди вариантов с лучшим охватом аварий и подключений, которые не доминируются по реакции, общему охвату, изменениям, времени дороги, потерянным назначениям и инженерам. Это фильтр Парето, а не строгое исполнение всей указанной последовательности. Модель может выбрать любую оставшуюся альтернативу. Метры и сумма начал high/urgent в этот фильтр не входят. Источники: [prompt и проверка ответа](../../src/field_router/llm.py#L121), [рейтинг и фильтр](../../src/field_router/llm.py#L163).

Рекомендация: один детерминированный контракт выбора на сервере; LLM объясняет проверенные выигрыши и потери. Названия профилей, метрики карточек, фильтр рекомендаций и тесты должны описывать одну политику.

## Предлагаемая политика

Общие требования сохраняются: допустимость окон, смен, навыков, транспорта и оборудования; учёт подтверждённых фактов и закреплённых работ; приоритет охвата аварии → подключения → остальные. Нельзя экономить километры, снимая доступную заявку. Вначале определяется лучший найденный вектор охвата, затем сравниваются планы только с этим вектором. Утверждённые назначения, потерянные при равном охвате, следует отдельно штрафовать или выводить как явный компромисс.

| Режим | Назначение | Предлагаемая вторичная цель после общего охвата |
|---|---|---|
| «Сохранить день» — обычный выбор диспетчера | Отмена, небольшое опоздание, обычный пересчёт | Потерянные прежние назначения → предотвратимые смены исполнителя → абсолютные сдвиги клиентских начал → минуты дороги → метры |
| «Быстрее к аварии» | Новое аварийное событие | Начало **этой** аварии минус момент поступления → стабильность → минуты дороги; при нескольких авариях нужна явно согласованная очередь, а не неявная сумма начал подключений |
| «Сократить дорогу» | Высвободить ресурс при допустимых изменениях | Минуты дороги → метры → стабильность; если освобождение смены имеет реальную избегаемую цену, учитывать её отдельно |

Для обычного события без новой аварии отдельный режим быстрого реагирования может отсутствовать. Если найден один уникальный или доминирующий вариант, показывать его и причины совпадения. Если есть компромисс, показывать разницу с «Сохранить день»: «авария раньше на X мин», «дороги меньше на Y мин / Z км», «изменено N назначений». Допустимые пределы переназначений/сдвигов должны быть явными настройками диспетчера; численные пороги данным аудитом не назначаются.

Stable должен исключать неизбежную смену выбывшего исполнителя из штрафа за переназначение, но по возможности сохранять исходное клиентское время. Для этого нужны раздельные reference времени и исполнителя. Счётчики «все изменения» и «изменения, которых можно было избежать» в объяснении также стоит разделить.

### Что значит экономическая цель

Сейчас в системе нет модели рублей. Число инженеров с работой в остатке дня не равно расходам на оплаченные смены: если инженер уже вышел и его оплата фиксирована, очистка его маршрута не возвращает эту оплату. Меньшее число инженеров может увеличить путь и задержать аварию. Сравнивать экономию только этим числом для дневного пересчёта недостаточно.

До появления проверенных тарифов честная цель — ресурсная: сохранять охват и согласованный уровень стабильности, уменьшать оставшиеся минуты дороги и показывать километры отдельно. Не называть эту величину денежной экономией. Утреннее решение о числе реально привлекаемых смен и дневное распределение уже работающих людей — разные решения.

Если предоставлены реальные избегаемые затраты, можно вычислять:

`C = Σ(тариф_км[транспорт] × км + тариф_мин[транспорт] × мин_дороги) + Σ(избегаемая_стоимость_нового_выхода) + стоимость_согласованных_изменений`.

Коэффициенты вводятся только из данных организации; двойной учёт одинаковых расходов исключается. Постоянная оплата уже открытой смены не включается как фиктивная экономия. Цена изменений учитывается только при наличии договорённой модели; иначе сохраняется отдельным ограничением или критерием. Сверхурочная работа сейчас запрещена ограничением смены и не добавляется незаметно как платная возможность. Все денежные слагаемые применяются **после** защиты охвата и согласованных эксплуатационных ограничений.

## Что проверить при реализации политики

1. Сохранять в дневных опытах все предложения: сигнатуру, ключ каждой цели, охват по приоритетам, реакцию, потери назначений, изменения, инженеров, минуты и метры. Сравнивать альтернативы одного и того же события/reference; отдельно фиксировать число уникальных планов.
2. Использовать общий явный вектор для проверки доминирования: неназначенные по трём ступеням, время реакции при новом событии, потери прежних назначений, смены, сдвиги, минуты дороги, инженеры, метры. Равенство и строгое доминирование считать раздельно; профильный выигрыш не называть улучшением всех метрик.
3. Добавить короткие регрессии: новая авария раньше ценой сдвига старой high; ресурсный вариант экономит дорогу ценой переназначения; устранение старого инженера сохраняет клиентское время; равный охват не скрывает потерю прежней заявки; три одинаковых результата сворачиваются в один; рекомендация совпадает с серверным правилом.
4. Для пользовательского вывода сравнить несколько дорожных дней/событий с одинаковыми входами и бюджетами. Существующие отчёты подтверждают допустимость, но не частоту выигрышей профилей.
